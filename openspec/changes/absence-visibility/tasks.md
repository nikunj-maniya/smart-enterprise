## 1. Visibility Policy

- [x] 1.1 Central visibility policy module: declarative §11A matrix → Prisma `where`/`select` shaping per viewer role _(Slice 1)_ — new `apps/api/src/modules/requests/visibility-policy.ts`: `resolveAbsenceScope(tenantId, viewer)` returns one of `{role:'hr'}` (HR Head, tenant-wide, full detail) / `{role:'management'}` (Enterprise Admin, tenant-wide, availability only) / `{role:'pm-tl'}` (Project Manager/Tech Lead, scoped to `ProjectMember` rows where they hold `PM`/`TL`) / throws 403 for every other role (Employee/Process Head/IT Admin — their own absences already surface via My Requests, no separate feed access). `canViewRequestDetail(viewerId, request)` is the existing requester-or-approver pending-detail gate, extracted so it's one named, testable function rather than inline logic.
- [x] 1.2 Route existing request list/detail endpoints through the policy module; tests per viewer role _(Slice 1)_ — `requests.service.ts`'s `getRequestById` now calls `canViewRequestDetail` instead of an inline `isRequester || isApprover` check (behavior unchanged, verified live: an unrelated employee still gets 404, an assigned approver still gets 200). `listMyRequests`/`listApprovalQueue` were already correctly self/approver-scoped structurally (no other code path could leak another user's requests) — the only genuinely new visibility surface is the absence feed (2.1), which is where the policy module's real work happens.
- [x] 1.3 Field stripping for Management-level viewers (reason/context never serialized) _(Slice 1)_ — `absences.service.ts` only spreads a `reason` key into the DTO when `scope.role === 'hr'`; for `management`/`pm-tl` viewers the key is genuinely absent from the JSON (not `null`), confirmed by inspecting the raw wire response live (see 5.3).

## 2. Absence Feed

- [x] 2.1 Absence range endpoint: approved Leave/WFH overlapping a month window, policy-scoped, with filters (department/project/type/person) _(Slice 2)_ — new `GET /absences` (`apps/api/src/modules/absences/`): queries `Request` where `status: 'Approved'`, `form.key in ('leave','wfh')`, and the range overlap `startDate <= to && endDate >= from` — "absences" are a query shape over the existing table, no denormalized model (design.md). Scoped via `resolveAbsenceScope`; further filterable by `projectId`/`departmentId`/`type`/`personId`. Verified live: HR/Admin/PM all see the same two approved Leave rows (full detail for HR, no `reason` key for Admin/PM), a still-pending third request in the same date range is invisible to HR too, and an Employee caller gets 403.
- [x] 2.2 Over-cap evaluation against the tenant's concurrent-absence cap _(Slice 2)_ — new `GET /absences/over-cap` (HR/Admin only, 403 for PM/TL — the warning panel is a Management-tier-only feature per design.md), walks each day in range counting concurrent approved absences against the cap. The cap itself is a new `GET`/`PUT /leave-types/absence-cap` (Enterprise Admin only) reading/writing `Tenant.settings.concurrentAbsenceCap` (existing JSON column — no migration needed), defaulting to 3. Verified live: set cap to 1, two overlapping approved leaves on the same two days correctly flagged with both people's names and `count: 2`; PM caller refused with 403.
