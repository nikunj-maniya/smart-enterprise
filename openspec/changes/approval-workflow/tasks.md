## 2. Decision Engine

- [x] 2.1 Decision service: authorize snapshotted approver, record Approve/Reject(+reason)/Comment, block double decisions _(Slice 2)_ — new `decisions.service.ts`'s `decideOnRequest()`. Verified live: a non-snapshotted user is refused (403); a second decision by the same approver is refused (409, optimistic `decision: 'pending'`-guarded update); a reject with no `comment` is refused (400).
- [x] 2.2 Outcome evaluation in the same locked transaction: all-approved → Approved, any-reject → Rejected, else stay pending _(Slice 2)_ — replaced the prior OR-gated shortcut (any single approve/reject immediately flipped the whole request) with real AND-gate arithmetic: `decideOnRequest` re-reads all snapshot rows inside its own transaction and only fires the outcome transition when none remain pending (approve) or immediately on any reject. Verified live on a real two-approver request: first approval leaves status `Pending Approval`; the second approval (a different snapshotted user) moves it to `Approved`. A separate two-approver request: one rejection (with reason) immediately moves it to `Rejected`, and the still-pending peer's row is reconciled to `rejected` with no comment of their own (moot-approval reconciliation, `reconcileRemainingApprovers` in `transitions.service.ts`).
- [x] 2.3 Audit-log every decision and outcome transition; emit events for notifications _(Slice 2)_ — an `AuditLog` row per individual decision (entity `RequestApprover`) plus the existing outcome-transition audit row; two new notification types added to the shared catalog and verified live: `request_decision_update` (to the requester, only on a non-final approve) and `approval_peer_decided` (to every other still-pending approver, on every decision) — closing a gap notifications-inapp's own spec named but couldn't yet trigger under the old OR-gate semantics.
- [x] 2.4 REST routes over the transport-agnostic decision service _(Slice 2)_ — `POST /requests/:id/decisions`; `transitionRequest` (the generic status-transition endpoint) now explicitly refuses `Approved`/`Rejected` targets whenever the request has a snapshotted approver set, directing those two outcomes exclusively through the decision endpoint (its authorization is snapshot-based, not the generic role gate).

## 3. Escalation

- [x] 3.1 Escalation-matrix table + seeded defaults (PM/TL/Manager → HR Head; HR Head → Enterprise Admin) + admin config API _(Slice 3)_ — new `EscalationRule` table (migration `20260710105114_approval_workflow_escalation`), keyed by `(tenantId, fromContext)` where `fromContext` matches `RequestApprover.roleContext` as actually produced (a `Role.key` when role-restricted, else the field's own key — e.g. Tech Lead's unrestricted picker context is `tech_lead`, not `tech-lead`). Seeded on tenant activation (`seedTenantEscalationDefaults`, `org-masters/seed.service.ts`) with PM→HR Head, `tech_lead`→HR Head, HR Head→Enterprise Admin; Process Head has no PRD-stated default. Admin config API: `GET/PUT /escalation-rules` (Enterprise Admin only) — no dedicated UI screen, matching this task's own scope (API only). Verified live: a freshly-registered tenant has the three rules seeded with correct target role names; a pre-existing tenant (registered before this change) has none, correctly falling through to the Enterprise Admin fallback.
- [x] 3.2 BullMQ sweep: escalate pending approvals on approved-leave overlap, deactivated approver, or action-window timeout — one hop, loop-safe, notifying original approver + requester _(Slice 4)_ — new `jobs/escalation-sweep.job.ts`, hourly repeatable job (design.md's decision overrides the Open-Questions note about tenant-configurable cadence — the action *window* is what's configurable, per rule; cadence is a fixed operational choice, matching the existing auto-complete job's own fixed schedule). Verified live end-to-end for the **inactive-approver** cause: deactivated the current approver, ran the sweep, confirmed reassignment to the matrix's next hop (falling back to Enterprise Admin when no other active holder of the target role exists) plus both parties notified (`approval_escalated`). The **on-leave** and **timeout** causes share the exact same reassignment/audit/notify code path (only the boolean cause-check differs) — not independently exercised against a real leave-overlap request, since building one requires the full leave form's picker chain; the shared mechanism they'd hit is the one already verified.
- [x] 3.3 Reassignment audit trail + chain annotation (from, to, cause) _(Slice 4)_ — `RequestApprover.escalatedFromId`/`escalationCause`/`escalatedAt` (same migration), a `RequestApprover`-entity `AuditLog` row per reassignment, and `escalatedFromName`/`escalationCause` surfaced on every chain entry (`GET /requests/:id`, the approvals-queue chain). Verified live: the audit log recorded `before: {approverId: <original>}, after: {approverId: <target>, cause: 'inactive'}` with `actorId: null` (system-triggered), and the request's chain showed `escalatedFromName`/`escalationCause` correctly.
