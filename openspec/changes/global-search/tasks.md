## 1. Search API

- [x] 1.1 Searcher registry + search endpoint (debounce-friendly, min 2 chars, grouped results capped per type) _(Slice 1)_ — new `GET /search?q=` (`apps/api/src/modules/search/`): `search.searchers.ts` holds one `Searcher` function per entity type, each capped to top 5 and returning `null` when not applicable/empty; `search.service.ts` fans out to the caller-tier's registered searchers concurrently and returns only non-empty groups. The 2-char minimum is enforced client-side by the overlay (design.md); the endpoint itself only requires non-empty `q`.
- [x] 1.2 Tenant searchers: users, projects, departments (role-gated, tenant-scoped) + own-requests searcher stub until request changes land _(Slice 1)_ — all four request changes this covers (leave-wfh, visitor, IT, approval-workflow) already landed earlier this session, so the "own requests" searcher is fully real, not a stub: matches by form title, scoped to `requesterId`. Users/projects reuse the exact tenant-scoped, active-only query `directory.service.ts` already uses for picker fields (design.md's "authorization by reuse"). Departments is Enterprise-Admin-gated, matching the Departments page's own `requireEnterpriseAdmin` guard. Verified live: an Employee's own-request search only ever returns their own requests (confirmed with two different tenant users searching the same term); a non-Admin gets no department results.
- [x] 1.3 System Admin searchers: enterprises, registrations, platform users _(Slice 1)_ — reuses `enterprises.service.ts`'s Active/Suspended scope, the Registrations queue's fields, and `users.service.ts`'s cross-tenant Platform Users listing (which is itself a cross-enterprise user list, not literally other System Admin accounts — matched to what the Platform Users *page* actually shows). Verified live as System Admin: searching a tenant's company name returns its enterprise + registration + all its users; searching a user's name returns them with their tenant name as the subtitle.
- [x] 1.4 pg_trgm indexes on searched name/title columns _(Slice 1)_ — migration `20260713054255_global_search_trgm_indexes`: enables `pg_trgm` and adds GIN trigram indexes on `User(name, email)`, `Project(name)`, `Department(name)`, `Tenant(name)`, `EnterpriseRegistration(companyName, contactName, contactEmail)` — the exact columns every searcher's `contains`/`insensitive` query (ILIKE under the hood) filters on.

## 3. Deep Links

- [x] 3.1 Result selection navigates to the owning screen with the record in view _(Slice 3)_ — `request` results reuse the pre-existing `?requestId=` param My Requests/Approvals Queue already used for notification deep-links (real detail-drawer open, not just the list). Every other type (user/project/department/enterprise/registration/platform-user) navigates to its owning list page with a new `?highlight=<id>` param; a small shared hook (`apps/web/src/lib/useHighlightRow.ts`) scrolls the matching row into view and gives it a brief brand-ring flash, reused identically across all six list pages.
