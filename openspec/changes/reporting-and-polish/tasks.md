## 1. Reporting & Exports

- [x] 1.1 Reporting endpoints over requests/approvals/absences through the visibility policy module _(Slice 1)_ — new `GET /reports/summary` (`apps/api/src/modules/reports/`): reuses `resolveAbsenceScope` (absence-visibility) verbatim for the same HR/management/PM-TL scoping, so an unauthorized role (Employee/Process Head/IT Admin) gets the identical 403 `/absences` already gives — no parallel permission code, per design.md. Returns request-volume counts (by form/status), average approval turnaround (creation → first Approved/Rejected `RequestStatusHistory` row, in hours), and an absence trend (day → concurrent count), the last of which is computed from the *same* `absences.service.ts` rows the calendar renders, not a re-derived query. Verified live: HR gets tenant-wide counts/turnaround/trend; an Employee gets 403.
- [x] 1.2 Dashboard screen with role-appropriate tiles _(Slice 1)_ — new `apps/web/src/pages/requests/Reports.tsx` (route `/reports`, nav entry visible to the same HR Head/Enterprise Admin/PM/Tech Lead set `resolveAbsenceScope` authorizes — backend is authoritative either way): month-range picker, a request-volumes bar list (by form + status), an average-approval-turnaround tile, an absence-trend bar list, and an "Export absences CSV" button. Deliberately basic — bar-list tiles built from plain divs, no charting dependency — matching the proposal's own "basic analytics" framing for a change explicitly flagged for re-slicing.
- [x] 1.3 CSV/Excel export of visible list/report views (streamed, visibility-scoped) _(Slice 2)_ — new `GET /reports/export` streams a CSV built directly from `absences.service.ts`'s `listAbsences` response — the `reason` column is only ever added to the header/rows when `scope === 'hr'`, and since that DTO already omits the `reason` key server-side for every other viewer (absence-visibility's field-stripping), the export structurally cannot leak it even if the CSV-building code had a bug in the header logic — there is no `reason` value anywhere in memory to accidentally serialize for a non-HR caller. **Disclosed scope reduction:** CSV only, not a real `.xlsx` — Excel opens CSV natively and this avoids a new spreadsheet-writing dependency for what the proposal itself calls "basic analytics." Verified live: HR's export has a `reason` column with the real text; Enterprise Admin's export of the identical range has no such column at all.

## 2. Notification Preferences

- [x] 2.1 Preference model + delivery-time filter in the notification dispatcher (mandatory types exempt) _(Slice 3)_ — new `User.notificationPreferences` JSON column (migration `20260713062728_notification_preferences`), a sparse `{[type]: {inApp?, slack?}}` map defaulting every unset entry to enabled (opt-out model). New `NOTIFICATION_TYPE_CATALOG` (`packages/shared/src/index.ts`) names every tenant-user-facing notification type + a `mandatory` flag (tenant policy) — only `request_needs_approval` is mandatory (an approver must always know work is waiting); `enterprise_registered` is System-Admin-only and excluded from this per-user catalog. `apps/api/src/modules/notifications/notification-preferences.ts`'s `isChannelEnabled` is the actual dispatcher filter, called from `notifications.service.ts`'s single `createAndEmit` chokepoint (the same one Slack mirroring already hooks) — mandatory types always pass; everything else is a straight lookup. Gates BOTH the in-app row/socket-push and the Slack mirror independently, so a user can mute one channel and keep the other.
- [x] 2.2 Activate the Profile page preference toggles against the new model _(Slice 3)_ — replaced the pre-existing "Coming soon" disabled 2-row (Email/Slack) stub in `apps/web/src/pages/Profile.tsx` with a real per-type table (one row per `NOTIFICATION_TYPE_CATALOG` entry, In-app/Slack toggle columns) backed by new `GET`/`PUT /profile/notification-preferences`. Email is correctly dropped — out of scope per design.md's non-goals, only in-app/Slack channels exist. Mandatory rows show a disabled, always-on toggle with a "Mandatory — cannot be muted" caption instead of the coarse blanket toggle the stub had.

- [x] 3.1 Add MinIO to docker-compose + signed-URL storage service _(Slice 4)_ — added a `minio` service to `docker-compose.yml` (ports 9500/API, 9501/console, healthchecked, persistent volume) and started it live in this environment. New `apps/api/src/lib/object-storage.ts` (`minio` npm client): `uploadObject`/`getSignedDownloadUrl`, bucket created lazily on first use, nothing in it ever made public — every read is a fresh, time-limited (`5min` default) presigned GET, matching design.md's "signed URLs only" decision exactly.
- [x] 3.2 Signature capture at visitor check-in, stored with consent on the record _(Slice 4)_ — new `Visitor.signatureObjectKey` column (migration `20260713064622_visitor_signature`, object key only, never a URL). New `POST /front-desk/:requestId/check-in` (`front-desk.service.ts`'s `checkInWithSignature`): decodes the canvas's `data:image/png;base64,...` payload, uploads it to MinIO, drives the identical `Approved → Checked-In` transition the plain check-in button already used, then updates the `Visitor` row's `signatureObjectKey`/`consent` together. New `GET /front-desk/:requestId/signature-url` returns a fresh signed URL, gated by the same Front-Desk role check (`EnterpriseAdmin`/`HrHead`) as the rest of that module. Frontend: new `SignaturePadModal.tsx` (canvas pointer-capture drawing + consent checkbox) replaces the plain "Check-in" button's direct transition call in `FrontDesk.tsx`; a new "Signature" button on Checked-In/Checked-Out rows opens the signed URL in a new tab.

## 4. Half-Day Dates & PWA

- [x] 4.1 Half-day specific-date selection in Leave/WFH wizards; balance math sums per-date weights _(Slice 5)_ — new generic form-engine field type `date-multi` (`packages/shared/src/form-engine/{metadata,compile}.ts`: an array-of-ISO-date-strings value, plus a new `DateMultiField.tsx` add-date/chip-list control wired into the shared `FormRenderer`/`FIELD_COMPONENTS` registry — reused by both Leave and WFH since both go through the same generic renderer, no separate wizard code to touch). `core-forms.ts`'s `half_day_count`/`half_wfh_count` number fields are replaced by `half_day_dates`/`half_wfh_dates`. The promoted `halfDayCount` column (balance math, absence calendar) is now derived as the dates array's length (`extractors.ts`) — the balance formula itself (`effectiveDays = totalDays - 0.5 * halfDayCount`, `leave-balance-ledger.ts`) is unchanged, since a count of half-day *dates* is mathematically the same input it always took. New `assertHalfDayDatesInRange` (`leave-wfh-rules.ts`) re-validates server-side that every selected date falls within `[start_date, end_date]`, mirroring the existing HR-signoff re-check's pattern. **Not built**, disclosed scope reduction consistent with this session's established renderer decision: no bespoke 3-step wizard UI — the generic `FormRenderer` renders this field like every other core-form field.
- [x] 4.2 PWA manifest + offline shell _(Slice 6)_ — new `apps/web/public/manifest.json` (installable, standalone display, brand icon/theme color) + `public/icon.svg` (the sidebar's own brand mark, reused rather than inventing new art) + `public/sw.js`, registered from `main.tsx`. **Disclosed approach:** the service worker runtime-caches same-origin GETs as they're visited (network-first, falling back to cache, falling back to the cached shell root) rather than precaching a build-time asset manifest — Vite's hashed bundle filenames make true precaching a heavier lift (a plugin dependency) than "a basic offline shell" calls for; the effect is the same for previously loaded views. Added a persistent `OfflineBanner` (`components/shell/OfflineBanner.tsx`, listens to `online`/`offline`) so the offline state is unambiguous rather than a silently stale screen, per the spec's own scenario wording. Verified live: `manifest.json`/`sw.js`/`icon.svg` all serve correctly (200) from the dev server. Not independently verified in a real installed-PWA offline session (no browser automation available in this environment).

- [x] 5.2 A muted optional notification type stops arriving; a mandatory one cannot be muted — verified live: muting `request_status_changed` (in-app) then triggering an EA-initiated status transition on the requester's own request produced no new notification row (count stayed at 3); attempting to mute the mandatory `request_needs_approval` type was refused with a 400. - [x] 5.4 A leave with two half-day dates deducts total − 1.0 — verified live on a fresh test tenant: a 4-day leave (Aug 10–13) with `half_day_dates: [Aug 10, Aug 13]`, approved by PM/TL/HR, deducted exactly `4 − 0.5×2 = 3.0` from the "Leaves available" balance (18 → confirmed 3 used). Also verified a half-day date outside the submitted range is refused server-side with a 400.
