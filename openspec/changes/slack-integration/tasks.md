## 2. Outbound Delivery

- [x] 2.1 BullMQ Slack delivery worker with retries; failures never block in-app notifications _(Slice 2)_ — new `apps/api/src/modules/slack/slack-delivery.ts` (`mirrorToSlack` enqueue, fire-and-forget, 3 attempts + exponential backoff) + `apps/api/src/jobs/slack-delivery.job.ts` (BullMQ `Worker`, started once on API boot). `mirrorToSlack` is called from `notifications.service.ts`'s single `createAndEmit` chokepoint — the exact same place every in-app notification is written — so no request/decision/transition code path needed touching directly, and an enqueue failure (caught, swallowed) can never affect the in-app write that already happened synchronously before it.
- [x] 2.2 Mirror triggers behind toggles: new request → approvers, decision/status change → requester _(Slice 2)_ — a `TRIGGER_TOGGLE` map in `slack-delivery.ts` maps each mirrored notification `type` to its tenant toggle: `request_needs_approval`→`notifyApproversOnNewRequest`, `request_approved`/`request_rejected`/`request_decision_update`→`notifyRequesterOnDecision`, `request_status_changed`→`notifyRequesterOnStatusChange`, `approval_reminder`→`reminderEnabled` (the last one incidentally also satisfies 4.2 — see below). Types absent from the map (e.g. `approval_peer_decided`, `approval_escalated`) are in-app only, per the spec's three named triggers. The worker resolves the target user's Slack id via `users.lookupByEmail` and DMs them (`chat.postMessage` with a user id as the channel). Not independently live-verified end-to-end (no real Slack workspace in this environment) — the gating logic (toggle off → no job dispatched at all, since `mirrorToSlack` returns early for unmapped/off types) is verified by code inspection and the config API's toggle persistence (1.1).

## 3. Interactive Actions

- [x] 3.1 Signed webhook endpoint: Slack signature + timestamp verification, then user matching by verified email _(Slice 3)_ — new `POST /slack/interactions` (`slack-webhook.routes.ts`), mounted with `express.raw()` ahead of the global JSON parser in `index.ts` (Slack's HMAC is over the exact raw bytes, and the payload is form-urlencoded, not JSON). `team_id` is read from the *unverified* body only to select which tenant's stored signing secret to check against (each tenant has its own Slack app/credentials — there's no single platform-wide secret), then `crypto.ts`'s `verifySlackSignature` (HMAC-SHA256 per Slack's documented v0 scheme, 5-minute replay window, constant-time compare) gates everything else. Verified live: a request with no `team_id` gets 400; a `team_id` with no connected `SlackConfig` gets 401 before any signature work happens; the signature algorithm itself was verified with a hand-computed HMAC in a throwaway script (valid signature accepted, tampered body/wrong secret/stale timestamp all correctly rejected). `matchSlackUserToPlatformUser` (`slack-interactions.service.ts`) resolves the Slack user's verified email via `users.info` and looks up an *active* platform user by that email in the same tenant — unmatched gets an ephemeral "not linked" reply (3.3).
- [x] 3.2 Approve action: authorize against platform permissions, record via the standard approval service, update the Slack message _(Slice 3)_ — `slack-interactions.service.ts`'s `handleBlockAction` calls the exact same `decideOnRequest` used by the in-app `POST /requests/:id/decisions` endpoint with the matched user's id — snapshot/authorization/audit/notification are byte-identical to in-app by construction (zero duplicated logic), not just "equivalent." A non-approver or already-decided request throws the same `HttpError` the in-app path throws, caught and shown as an ephemeral Slack reply. On success, `chat.update` replaces the original message's buttons with a "Approved by {name}" line.
- [x] 3.3 Reject action with reason modal; unmatched/unauthorized users get an explanatory ephemeral reply _(Slice 3)_ — clicking Reject opens a Slack modal (`views.open`, reason as a required `plain_text_input`) instead of deciding immediately; the `view_submission` payload (a second, independently-verified webhook call) carries the reason and calls `decideOnRequest(..., 'rejected', reason)` — which itself throws 400 if the reason is empty, identical to the in-app rule, no separate check needed. Unmatched Slack users are refused with an ephemeral reply at the *first* click, before a modal is ever opened.

## 4. Digest & Reminders

- [x] 4.1 Daily absence digest job (configured channel/time, availability-level content only) _(Slice 4)_ — new `apps/api/src/jobs/slack-digest.job.ts`: since BullMQ has no native per-tenant cron, a single repeatable job ticks every 15 minutes, and each connected + digest-enabled tenant is checked against *its own* configured `digestTime` in Asia/Kolkata (design.md); a `lastDigestSentDate` column guards against sending twice in one day. Content is name/type/date-range only — reused directly from the same `Request` query shape `absences.service.ts` (absence-visibility) uses, deliberately not calling that HR-scoped service (this is a channel-wide broadcast, not a per-viewer query) but built to the identical availability-only field set, so reason/context can never appear in a channel post.
- [x] 4.2 Daily pending-approval reminder to approvers with open items; never auto-decides _(Slice 4)_ — no new job needed: the existing daily in-app `approval-reminders.job.ts` (from `notifications-inapp`) already calls `notify()` per approver with `type: 'approval_reminder'`, which is now one of the mirrored types (2.2) gated by the new `reminderEnabled` toggle — it automatically gets a Slack DM mirror with zero changes to that job. A reminder is purely informational (a DM listing a pending count); nothing in this path ever calls `decideOnRequest` or any transition, so it structurally cannot auto-decide anything.
