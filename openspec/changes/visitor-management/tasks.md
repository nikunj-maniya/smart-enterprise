## 1. Visitor Registration

- [x] 1.1 Add the Visitor core `FormDefinition` metadata (fields, validation, Process Head routing) + seed _(Slice 1)_ — pre-existed from `form-engine`'s `core-forms.ts`.
- [x] 1.2 Registration endpoint: validate (Zod), enforce consent + conditional day-count server-side, create request `Pre-Registered` with snapshotted Process Head approver _(Slice 1)_ — validation/consent/gated-day-count already worked generically (form-engine's rule engine — required `consent-link`, `no_of_days` gated on `will_come_next_days`). **Found and fixed the same class of bug as leave-wfh-requests**: Visitor's seeded status model starts at `Pre-Registered` with nothing ever advancing it to `Pending Approval`, so every submission was stuck forever and the Process Head could never see it. Generalized the fix beyond a Visitor-specific patch: `forms.service.ts`'s `getPublishedDefinitionForSubmission` now resolves the *effective* initial status by walking any leading chain of placeholder states nobody but the requester could ever act on (stops the instant a state has a non-requester action) — this also transparently fixes IT's identical `Requested → Pending Approval` gap ahead of that change. A first version of this fix was itself buggy (picked an arbitrary requester-gated branch, including Visitor's own `-> Cancelled` escape hatch, landing new registrations in `Cancelled`) — caught during live verification and corrected. Verified live: submission now lands in `Pending Approval` and the Process Head sees it immediately.
- [ ] 1.3 Build the Visitor form screen per the design (directory picker, gadget fields, gated no-of-days, consent link + checkbox) _(Slice 1)_ — **scope reduction, not built**: same as `leave-wfh-requests`, the existing generic single-page `RequestForm`/`FormRenderer` renders the Visitor form as-is (all fields, pickers, and the gated no-of-days already work — verified live), rather than the design's bespoke layout.
- [x] 1.4 Wire the Process Head approval stage: approve → `Approved`, reject with reason → `Cancelled`, host notified _(Slice 2)_ — approval already worked via the generic decision engine. **Found and fixed a real gap**: the decision engine hardcoded `'Rejected'` as the reject-outcome state name, but Visitor has no such state (its rejection target is `Cancelled`) — a Process Head's reject would have thrown a 400. Generalized `decisions.service.ts` to resolve the reject-outcome name dynamically (prefer a declared `-> Rejected` transition; fall back to `Cancelled`), and generalized the requester-notification logic (`transitions.service.ts`) to key off an explicit decision-outcome signal rather than string-matching the target state name, so a Visitor rejection now correctly fires `request_rejected` (with reason) instead of a generic status-changed notification. Verified live end-to-end.
